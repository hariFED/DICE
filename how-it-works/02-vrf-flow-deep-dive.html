VRF Round Deep Dive

How DICE Generates Verifiable Randomness — From Request to Callback
DICE Protocol • Technical Reference • v3.0
Commit-Reveal Solana On-Chain ESP32-S3 Hardware ECDSA secp256k1 SHA-256 Binding
Creator — Full Implementation Detail Judge — Cryptographic Security Analysis
What happens when someone requests randomness from DICE? A 6-step cryptographic pipeline executes across Solana, a Rust coordinator, and 4–7 ESP32-S3 hardware nodes. The entire flow takes 1.3–1.7 seconds (p50) and has completed 545+ consecutive rounds with zero failures.
  • On-chain request locks 0.002 SOL in escrow and creates a verifiable PDA
  • Unpredictable node selection uses SlotHashes sysvar + Fisher-Yates shuffle
  • Hardware entropy from 3 physical sources, mixed via XOR and finalized with SHA-256
  • Commit-reveal protocol ensures no participant can see others' entropy before committing
  • CPI callback delivers 32 bytes of randomness directly to the developer's program

End-to-End Flow

Follow the randomness from request to delivery
1

REQUEST On-Chain

Developer calls request_randomness(sequence, callback_program_id). A RandomnessRequest PDA is created with status = Pending. An escrow PDA locks 0.002 SOL (2,000,000 lamports). The coordinator detects this event via Solana WebSocket subscription.

2

NODE SELECTION On-Chain

Coordinator calls select_nodes(round_id). The SlotHashes sysvar provides the most recent slot hash (32 bytes of unpredictable chain state). Combined with channel key, round ID, and block height via SHA-256, this seed drives a Fisher-Yates shuffle over all registered devices. 4–7 nodes are selected. No one can predict or manipulate the selection.

3

COMMIT ESP32-S3 Hardware

Each selected node generates 32 bytes of entropy from 3 physical sources (TRNG, floating ADC, timing jitter), mixed via XOR and finalized with SHA-256. The node computes commit_hash = SHA-256(entropy), signs it with ECDSA secp256k1, and sends the CommitSubmission via WebSocket. The entropy itself remains secret on the device.

4

REVEAL ESP32-S3 + Coordinator

After all commits are collected, the coordinator broadcasts the reveal signal. Each node sends its raw entropy + ECDSA signature. The coordinator verifies SHA-256(entropy) == commit_hash and recovers the signer from the ECDSA signature to confirm it matches the registered device pubkey. The on-chain submit_reveal instruction enforces both checks.

5

FINALIZE On-Chain

The coordinator calls finalize_randomness. The program computes SHA-256(entropy_1 || entropy_2 || ... || entropy_n) from all RevealRecord PDAs. A RandomnessResult PDA is created containing the 32-byte output. If a callback was registered, the program CPI-invokes dice_callback(request_key, randomness) on the developer's program.

6

PAYOUT On-Chain

The 0.002 SOL escrow is distributed: 70% split equally among contributing nodes, 20% to protocol treasury, 10% to reserve. claim_rewards is called once per contributing node, transferring lamports directly from the escrow PDA.

1

REQUEST — On-Chain

Solana Developer-initiated

What the Developer Does Creator

The developer calls a single Solana instruction to initiate a VRF round. The only required inputs are a sequence number (monotonically increasing per requester) and a callback_program_id (the program that will receive the randomness via CPI).

Rust / Anchor Instruction
pub fn request_randomness( ctx: Context<RequestRandomness>, sequence: u64, callback_program_id: Pubkey, ) -> Result<()>
Creator note: If you don't want a callback, pass Pubkey::default() as the callback_program_id and poll the RandomnessResult PDA instead.

What Happens On-Chain Judge

  • Escrow PDA created — 0.002 SOL (2,000,000 lamports) transferred from requester to escrow. The escrow is a PDA seeded with [b"escrow", requester, sequence_le], making it impossible to drain before finalization.
  • RandomnessRequest PDA created — Seeds: [b"request", requester, sequence_le]. Fields initialized: status = Pending, node_count = 0, commits_received = 0, reveals_received = 0.
  • Commit deadline set — commit_deadline_slot = current_slot + 150 (~60 seconds at Solana's ~0.4s/slot).
  • Event emitted — Solana logs "Randomness requested by {requester} seq={sequence} at slot {slot}".
// PDA derivation for the request account
find_program_address(
  seeds: [b"request", requester.key(), &sequence.to_le_bytes()],
  program_id: DICE_PROGRAM_ID
)

// PDA derivation for the escrow account
find_program_address(
  seeds: [b"escrow", requester.key(), &sequence.to_le_bytes()],
  program_id: DICE_PROGRAM_ID
)
Security analysis: The escrow PDA is program-owned. Only the DICE program can authorize transfers out of it, and only after a round is fully finalized (status = Finalized) and a contributing device is verified. This prevents fee-skimming or premature withdrawal.

Coordinator Detection

The Rust coordinator runs a Solana WebSocket subscription (accountSubscribe) monitoring for new RandomnessRequest PDAs. When one appears with status = Pending, the coordinator inserts a new entry into its in-memory RoundMap and begins orchestration.

2

NODE SELECTION — On-Chain

SlotHashes Fisher-Yates

How Nodes Are Chosen Creator

The coordinator submits a select_nodes(round_id) transaction. The on-chain program reads the SlotHashes sysvar, which contains the hashes of the 512 most recent slots. These hashes are produced by Solana's Proof-of-History clock and cannot be predicted or influenced by any single participant.

On-Chain Seed Computation
// Extract 32 bytes from the most recent slot hash let recent_slot_hash: &[u8] = &slot_hashes_data[16..48]; // Deterministic seed = SHA-256(slot_hash || channel_key || round_id || block_height) let seed_hash = hashv(&[ recent_slot_hash, channel_key.as_ref(), &round_id_bytes, &block_height_bytes, ]);

Fisher-Yates Shuffle Judge

A Fisher-Yates (Knuth) shuffle permutes the list of all registered, active devices. For each index i from n-1 down to 1, a swap index j is computed as:

// For each index i, derive a unique pseudo-random j let idx_hash = hashv(&[&seed_bytes, &(i as u64).to_le_bytes()]); let j = u64::from_le_bytes(idx_hash[0..8]) as usize % (i + 1); indices.swap(i, j);

The first node_count (4–7) entries from the shuffled list become the selected nodes. Their compressed secp256k1 pubkeys (33 bytes each) are written to the channel PDA.

Security analysis: The seed depends on SlotHashes (unpredictable PoH output), the channel key (fixed per channel), the round ID, and the current block height. An attacker would need to control the Solana validator that produces the slot hash and predict the exact block height at execution time. Each shuffle step re-hashes with the loop index, so learning one swap position reveals nothing about the next. This achieves computational unpredictability under the assumption that the slot hash oracle is honest (guaranteed by Solana's leader rotation).

COMMIT PHASE — ESP32-S3 Hardware

Hardware Entropy SHA-256 Commit

Job Assignment Creator

The coordinator sends a JobAssignment message to each selected node via WebSocket (CBOR-encoded, mTLS-secured). The message contains:

  • request_id — 32-byte on-chain request identifier
  • round_seq — monotonically increasing sequence number
  • deadline_ts — Unix timestamp by which the node must commit
CBOR Wire Format (Firmware Integer-Key Map)

ADC Noise Collection Judge

The firmware reads 8 samples from ADC1 Channel 0 (GPIO1), configured at 12-bit resolution with full 0–3.3V attenuation. The pin is intentionally left unconnected (floating), so it picks up thermal noise and electromagnetic interference. Each sample is folded into the accumulator via rotate-left-4 + XOR:

for (int i = 0; i < 8; i++) { int raw = 0; adc_oneshot_read(handle, ADC_CHANNEL_0, &raw); noise = ((noise << 4) | (noise >> 28)) ^ (uint32_t)raw; }
Security analysis: Even if the ADC source fails (returns zero or constant values), the entropy remains valid because TRNG provides the primary 32 bytes. The ADC and timer sources are additive entropy: they can only increase randomness, never decrease it (XOR with an independent source preserves or improves entropy). The SHA-256 finalization then acts as a randomness extractor, producing a uniform 32-byte output regardless of the entropy distribution.

Commit Hash and Signature

After entropy generation, the firmware computes the commit and signs it:

// Step 1: Compute commit hash dice_crypto_sha256(entropy, 32, commit_hash); // commit_hash = SHA-256(entropy) // Step 2: Sign commit_hash with device's secp256k1 private key dice_crypto_sign(commit_hash, 32, signature); // ECDSA(commit_hash) -> 64 bytes [r||s] // Step 3: Get compressed public key (33 bytes, 0x02/0x03 prefix) dice_crypto_get_pubkey(node_id); // node_id = compressed secp256k1 pubkey

The entropy is then stored in a local job queue (ring buffer, max 16 slots) for later reveal. The CommitSubmission message is sent to the coordinator:

CommitSubmission Wire Format
request_id : bytes(32) // on-chain request ID node_id : bytes(33) // compressed secp256k1 pubkey commit_hash : bytes(32) // SHA-256(entropy) signature : bytes(64) // ECDSA signature over commit_hash

On-Chain Commit Recording Judge

The coordinator relays each commit to Solana via submit_commit(device_id, device_pubkey, commit_hash). The on-chain program:

  • Verifies device_id == SHA-256(device_pubkey) (prevents ID spoofing)
  • Checks the request status is Pending or CommitPhase
  • Checks the commit deadline has not passed (current_slot <= commit_deadline_slot)
  • Checks the device has not already committed (no duplicate commits)
  • Creates a CommitRecord PDA seeded with [b"commit", requester, sequence, device_id]
  • Transitions status to CommitPhase and increments commits_received
Security analysis: The commit is recorded on-chain before the reveal phase begins. This means once a node commits, its entropy is cryptographically bound. The node cannot change its entropy after seeing other nodes' commits. SHA-256 is collision-resistant (no known practical collision attacks), so no two distinct entropy values can produce the same commit hash.
4

REVEAL PHASE — ESP32-S3 + On-Chain

Hash Verification ECDSA Recovery

Reveal Signal and Submission Creator

After all expected commits are collected (or the commit timeout is reached with enough commits), the coordinator broadcasts a reveal signal to all participating nodes. Each node:

  1. Looks up the stored entropy from its local job queue by request_id
  2. Signs the raw entropy with its secp256k1 private key
  3. Sends a RevealSubmission containing the entropy + signature
  4. Scrubs the entropy from local memory and marks the job slot as free
RevealSubmission Wire Format
request_id : bytes(32) // on-chain request ID node_id : bytes(33) // compressed secp256k1 pubkey entropy : bytes(32) // raw entropy (the preimage) signature : bytes(64) // ECDSA signature over entropy

On-Chain Verification: Two Critical Checks Judge

The submit_reveal instruction performs two critical verifications that are the cryptographic backbone of the protocol:

CHECK 1: Hash Binding

// Verify entropy matches prior commit let entropy_hash = hashv(&[&entropy]); require!( entropy_hash.to_bytes() == commit_record.commit_hash, DiceError::RevealMismatch );

If SHA-256(revealed_entropy) != commit_hash, the transaction is rejected. The node cannot retroactively change its entropy.

CHECK 2: Signature Verification

// Recover signer from ECDSA sig let msg_hash = keccak::hash(&entropy); let recovered = secp256k1_recover( msg_hash, recovery_id, &sig )?; // Compress and compare require!( compressed == device_pubkey, DiceError::InvalidSignature );

Uses secp256k1_recover with Keccak-256 message hash. The recovered public key is compressed and compared to the registered device pubkey.

Security analysis: These two checks together ensure: (1) the entropy was committed to before the reveal phase, and (2) it was produced by the specific registered hardware device. An attacker who compromises the coordinator cannot forge reveals, because they would need the device's private key to produce a valid ECDSA signature. The use of Keccak-256 for signature hashing (Ethereum convention) and SHA-256 for commit hashing provides domain separation between the two checks.

State Transitions

On the first reveal, the request transitions from CommitPhase to RevealPhase and the reveal deadline is set (current_slot + 150). A RevealRecord PDA is created for each valid reveal, storing the entropy, signature, and device pubkey. The reveals_received counter is incremented.

FINALIZE — On-Chain

SHA-256 Combine CPI Callback

Randomness Combination Judge

The finalize_randomness instruction reads all RevealRecord PDAs passed as remaining accounts, extracts their entropy values, and computes the final randomness:

// Concatenate all entropy values and hash let refs: Vec<&[u8]> = entropy_slices.iter().map(|e| e.as_ref()).collect(); let final_hash = hashv(&refs); // SHA-256(entropy_1 || entropy_2 || ... || entropy_n) let final_bytes = final_hash.to_bytes(); // 32-byte randomness output

A minimum of 4 reveals (MIN_NODES_REQUIRED = 4) is enforced. If fewer reveals are received by the deadline, the round transitions to Failed status.

CPI Callback to Developer Program Creator

If the developer registered a callback_program_id, the DICE program constructs and invokes a CPI call. The developer's program must implement a dice_callback instruction with this exact discriminator:

// Discriminator: SHA-256("global:dice_callback")[0..8] const DICE_CALLBACK_DISCRIMINATOR: [u8; 8] = [128, 131, 129, 45, 53, 113, 215, 151]; // Callback instruction data layout (72 bytes total): // [0..8] discriminator // [8..40] request_key (Pubkey, 32 bytes) // [40..72] randomness ([u8; 32])

The callback receives the RandomnessResult PDA as its first account (read-only), so the developer's program can independently verify the randomness is authentic by checking the PDA owner is the DICE program.

Creator note: Your program's dice_callback signature must be: pub fn dice_callback(ctx: Context<...>, request_key: Pubkey, randomness: [u8; 32]) -> Result<()>

RandomnessResult PDA Judge

The finalized result is stored permanently on-chain in a RandomnessResult PDA (312 bytes):

  • request — Pubkey linking back to the original request
  • randomness — The 32-byte final output
  • contributing_nodes — Up to 7 compressed secp256k1 pubkeys
  • contributing_count — Number of nodes that contributed
  • finalized_slot — Solana slot at which finalization occurred

Security analysis: The result is fully auditable. Any observer can read the RandomnessResult PDA, trace back to each RevealRecord PDA (to see individual entropy contributions), verify each CommitRecord (to confirm the hashes match), and independently recompute SHA-256(entropy_1 || ... || entropy_n) to verify correctness. This is a fully transparent, on-chain audit trail.

Per-Node Reward Calculation

With 5 contributing nodes, each node receives:

total_node_share = 2,000,000 * 7,000 / 10,000 = 1,400,000 lamports per_node_share = 1,400,000 / 5 = 280,000 lamports (0.00028 SOL) treasury_share = 2,000,000 * 2,000 / 10,000 = 400,000 lamports reserve_share = 2,000,000 * 1,000 / 10,000 = 200,000 lamports
Creator note: The BPS (basis points) system uses integers only — no floating-point arithmetic. NODE_REWARD_BPS(7000) + TREASURY_REWARD_BPS(2000) + RESERVE_REWARD_BPS(1000) = 10000 (exactly 100%), verified by on-chain unit tests. The fee of 2,000,000 lamports divides cleanly with zero rounding dust.

Escrow PDA-Signed Transfers Judge

The claim_rewards instruction uses PDA signer seeds to authorize transfers out of the escrow. The program reconstructs the PDA with [b"escrow", requester, sequence_le, bump] and passes it as a signer to the system program transfer CPI. This means:

  • Only the DICE program can move funds from the escrow — no external wallet holds the key
  • The is_claimed flag prevents double-claiming
  • The instruction verifies the device_pubkey appears in the contributing_nodes array of the RandomnessResult
  • The request must be in Finalized status
Security analysis: The escrow is fully trustless. No human holds the private key for the escrow PDA — it is derived deterministically by the Solana runtime. The DICE program is the only entity that can sign with these seeds, and only under the verified conditions (finalized round, contributing node, not yet claimed). This eliminates all custodial risk.

Why This Is Secure — Threat Model Analysis

Judge Focus

Commit-Reveal Protocol

No participant sees any other participant's entropy until all have committed. Once committed, the SHA-256 hash binding prevents retroactive modification. An attacker who withholds their reveal can at most cause a round to fail (denial of service), but cannot bias the output — the round simply retries with the remaining nodes.

Multi-Node XOR + SHA-256

The final randomness is SHA-256(e1 || e2 || ... || eN). Even if N-1 of the N nodes are adversarial and colluding, the single honest node's entropy ensures the output is computationally indistinguishable from random (under SHA-256 as a random oracle). This is the "1-out-of-N honest" security property — the strongest achievable.

Hardware Entropy (Not Software PRNG)

Each ESP32-S3's entropy comes from a hardware TRNG (ring oscillator sampling quantum thermal noise), supplemented by a floating ADC pin and timing jitter. This is physically random — no seed, no state, no periodicity. A software attacker who compromises the firmware cannot predict the TRNG output without physical access to the chip.

ECDSA secp256k1 Authentication

Every message from every node is signed with the device's unique secp256k1 private key, stored in NVS (non-volatile storage). The on-chain program recovers the public key from the signature and compares it to the registered device pubkey. Impersonation requires possession of the physical device's private key material.

On-Chain Verification

All critical checks (hash binding, signature verification, node authorization, deadline enforcement) are performed by the Solana program, not the coordinator. The coordinator is a convenience layer — even a fully compromised coordinator cannot forge valid on-chain transactions because it does not hold device private keys.

Unpredictable Node Selection

The Fisher-Yates shuffle seed derives from the SlotHashes sysvar (PoH output), the channel key, round ID, and block height. Predicting which nodes will be selected requires controlling Solana's validator schedule. An attacker who operates some nodes cannot ensure they are selected for a given round.
