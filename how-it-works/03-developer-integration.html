Developer Guide

Integrate DICE VRF in Your Program

Add provable, hardware-backed randomness to any Solana program. One callback function, zero external SDKs, verifiable on-chain. This guide covers everything from the 4-line minimum to production-ready examples.

Is It Really 4 Lines? Core Concept

The core integration with DICE VRF is a single callback function. DICE calls your program via CPI when randomness is ready. Here is the absolute minimum:

Rust minimum_integration.rs 
// 1. Define the callback handler
pub fn dice_callback(
    ctx: Context<MyCallback>,
    _channel_key: Pubkey,
    randomness: [u8; 32],
) -> Result<()> {
    // 2. Use the randomness
    let result = randomness[0] % 6 + 1; // dice roll 1-6
    ctx.accounts.game.result = result;
    Ok(())
}
💡
That is genuinely the core integration. DICE invokes your dice_callback function with 32 bytes of hardware-generated randomness via CPI. You transform those bytes into your game logic. But you also need account structs, game state, and payout logic — which is what the rest of this guide covers.

What the callback signature means

Parameter Type Description
ctx Context<YourAccounts> Your program's accounts, passed by the coordinator as remaining_accounts
_channel_key Pubkey The DiceChannel PDA that produced the randomness (useful for multi-channel setups)
randomness [u8; 32] 32 bytes of hardware-generated, commit-reveal verified randomness

The function name must be dice_callback. DICE uses the Anchor discriminator SHA-256("global:dice_callback")[0..8] to locate it in your program. This is the same pattern Anchor uses for all instruction dispatch.

Full Integration Walkthrough Complete

Let's build a complete dice game step by step. Players bet on a number 1-6, wager SOL, and DICE VRF determines the outcome. Winners receive 5x their wager.

1

Define Your Game State

Every game needs state accounts to track players, bets, and outcomes. In Anchor, these are #[account] structs stored as PDAs.

Rust state.rs — Game accounts 
/// House account — tracks overall game statistics.
#[account]
pub struct House {
    pub authority: Pubkey,             // house owner
    pub total_rolls: u64,             // lifetime roll count
    pub roll_distribution: [u64; 6], // [count_1, count_2, ..., count_6]
    pub bump: u8,                     // PDA bump seed
}

impl House {
    const LEN: usize = 32 + 8 + (6 * 8) + 1; // 89 bytes
}

/// Roll account — one per player per bet.
#[account]
pub struct Roll {
    pub player: Pubkey,        // who placed this bet
    pub bet: u8,              // 1-6
    pub wager: u64,           // lamports wagered
    pub roll_id: u64,         // unique identifier (prevents dupes)
    pub result: u8,           // 1-6 (0 = unresolved)
    pub settled: bool,        // true after callback received
    pub randomness: [u8; 32], // raw VRF output (for audit)
    pub bump: u8,             // PDA bump seed
}

impl Roll {
    const LEN: usize = 32 + 1 + 8 + 8 + 1 + 1 + 32 + 1; // 84 bytes
}
✔
Design pattern: Store the raw 32-byte randomness in your game account. This lets anyone independently verify the result on-chain — full auditability without trusting your math.
2

Create the Betting Instruction

The roll_dice instruction validates the bet, creates a Roll PDA, and transfers the wager to a vault. After this transaction confirms, the coordinator detects the pending request and dispatches it to ESP32 hardware nodes.

Rust instructions/roll_dice.rs 
pub fn roll_dice(
    ctx: Context<RollDice>,
    bet: u8,
    wager: u64,
    roll_id: u64,
) -> Result<()> {
    // Validate inputs
    require!(bet >= 1 && bet <= 6, DiceRollError::InvalidBet);
    require!(wager > 0, DiceRollError::ZeroWager);

    // Initialize the Roll account
    let roll = &mut ctx.accounts.roll;
    roll.player = ctx.accounts.player.key();
    roll.bet = bet;
    roll.wager = wager;
    roll.roll_id = roll_id;
    roll.result = 0;         // unresolved
    roll.settled = false;
    roll.randomness = [0u8; 32];
    roll.bump = ctx.bumps.roll;

    // Transfer wager to vault PDA
    let cpi_ctx = CpiContext::new(
        ctx.accounts.system_program.to_account_info(),
        anchor_lang::system_program::Transfer {
            from: ctx.accounts.player.to_account_info(),
            to: ctx.accounts.vault.to_account_info(),
        },
    );
    anchor_lang::system_program::transfer(cpi_ctx, wager)?;

    msg!("Dice roll: bet={}, wager={} lamports", bet, wager);
    Ok(())
}

#[derive(Accounts)]
#[instruction(bet: u8, wager: u64, roll_id: u64)]
pub struct RollDice<'info> {
    #[account(mut)]
    pub player: Signer<'info>,

    #[account(
        init, payer = player,
        space = 8 + Roll::LEN,
        seeds = [b"roll", player.key().as_ref(), &roll_id.to_le_bytes()],
        bump,
    )]
    pub roll: Account<'info, Roll>,

    /// CHECK: vault PDA holds lamports
    #[account(mut, seeds = [b"vault"], bump)]
    pub vault: AccountInfo<'info>,

    pub system_program: Program<'info, System>,
}
3

Implement dice_callback

This is where DICE delivers randomness to your program. The coordinator calls deliver_callback on the DICE program, which CPI-invokes your dice_callback. Your accounts are passed as remaining_accounts.

Rust instructions/dice_callback.rs — The Integration Point 
/// Called by DICE VRF after hardware nodes generate randomness.
///
/// Converts 32 bytes of entropy into a dice roll (1-6).
/// Uses first 4 bytes as u32 for better distribution.
pub fn dice_callback(
    ctx: Context<DiceRollCallback>,
    _channel_key: Pubkey,
    randomness: [u8; 32],
) -> Result<()> {
    let roll = &mut ctx.accounts.roll;
    require!(!roll.settled, DiceRollError::AlreadySettled);

    // Convert randomness to dice roll (1-6)
    // Use first 4 bytes as u32 for better distribution
    let rand_u32 = u32::from_le_bytes([
        randomness[0], randomness[1],
        randomness[2], randomness[3],
    ]);
    let result = (rand_u32 % 6) as u8 + 1;

    // Store everything for audit
    roll.randomness = randomness;
    roll.result = result;
    roll.settled = true;

    // Update house statistics
    let house = &mut ctx.accounts.house;
    house.total_rolls += 1;
    house.roll_distribution[(result - 1) as usize] += 1;

    let won = result == roll.bet;
    msg!("Rolled: {}. Bet: {}. {}!", result, roll.bet,
         if won { "WIN" } else { "LOSE" });
    Ok(())
}

#[derive(Accounts)]
pub struct DiceRollCallback<'info> {
    #[account(mut)]
    pub roll: Account<'info, Roll>,

    #[account(mut, seeds = [b"house"], bump = house.bump)]
    pub house: Account<'info, House>,
}
⚠
Distribution bias note: Using randomness[0] % 6 (single byte) has a 1.56% bias because 256 is not evenly divisible by 6. The actual code uses u32::from_le_bytes(randomness[0..4]) % 6 which reduces bias to 0.0000001% (4,294,967,296 mod 6 = 4). For cryptographic applications, use rejection sampling.
4

Create the Claim Instruction

After the callback settles the game, winning players call claim to collect their payout from the vault PDA.

Rust instructions/claim.rs 
/// Player claims winnings (5x wager) after a winning roll.
pub fn claim(ctx: Context<ClaimRoll>) -> Result<()> {
    let roll = &ctx.accounts.roll;
    require!(roll.settled, DiceRollError::NotSettled);
    require!(roll.result == roll.bet, DiceRollError::PlayerLost);

    let payout = roll.wager * 5; // 1-in-6 chance, 5x payout = 16.7% house edge

    // Direct lamport transfer from vault to player
    **ctx.accounts.vault.to_account_info().try_borrow_mut_lamports()? -= payout;
    **ctx.accounts.player.to_account_info().try_borrow_mut_lamports()? += payout;

    msg!("Payout: {} lamports to {}", payout, ctx.accounts.player.key());
    Ok(())
}

#[derive(Accounts)]
pub struct ClaimRoll<'info> {
    #[account(mut)]
    pub player: Signer<'info>,

    #[account(
        mut,
        has_one = player,
        constraint = roll.settled @ DiceRollError::NotSettled,
    )]
    pub roll: Account<'info, Roll>,

    /// CHECK: vault PDA holds lamports
    #[account(mut, seeds = [b"vault"], bump)]
    pub vault: AccountInfo<'info>,
}

What DICE Handles vs. What You Write

DICE Handles (The Hard Part)

  • Protocol fee collection (0.002 SOL per request)
  • Node coordination and job dispatch
  • ESP32-S3 hardware entropy generation
  • Commit-reveal protocol enforcement
  • ECDSA signature verification per node
  • SHA-256 hash binding (commit matches reveal)
  • Multi-node entropy combination
  • CPI callback delivery to your program
  • Fee distribution (70% nodes / 20% treasury / 10% reserve)
  • Timeout handling and round failure recovery
  • On-chain verifiable node selection

You Write (The Fun Part)

  • Game logic (how randomness maps to outcomes)
  • State management (player accounts, game accounts)
  • Input validation (bet ranges, wager limits)
  • Payout rules (multipliers, house edge)
  • The dice_callback function
  • Account structs for your game
  • Claim/settlement mechanics
  • Frontend UI (when you build one)

Callback Data Format

When DICE calls your dice_callback, it constructs 72 bytes of instruction data:

[0..8] discriminator 8 bytes
[8..40] channel_key 32 bytes — Pubkey
[40..72] randomness 32 bytes — [u8; 32]
Rust Discriminator computation (for reference) 
// The discriminator is the first 8 bytes of:
//   SHA-256("global:dice_callback")
// = [128, 131, 129, 45, 53, 113, 215, 151]

const DICE_CALLBACK_DISCRIMINATOR: [u8; 8] =
    [128, 131, 129, 45, 53, 113, 215, 151];

// You do NOT need to use this constant yourself.
// Anchor handles discriminator matching automatically
// when you name your function `dice_callback`.
🔗
How CPI delivery works under the hood:
  1. DICE's deliver_callback instruction is called by the coordinator
  2. It reads channel.callback_program_id and channel.randomness
  3. It builds a 72-byte instruction and invokes your program via solana_program::program::invoke
  4. Your accounts are forwarded from the coordinator's remaining_accounts[1..]
  5. If the CPI fails, the channel reverts to Finalized so delivery can be retried

Example 2: Lucky Wheel

Weighted segment selection Configurable wheel with up to 10 segments, each with custom weight and multiplier.

Rust programs/lucky-wheel/src/lib.rs — Callback 
pub fn dice_callback(
    ctx: Context<WheelCallback>,
    _channel_key: Pubkey,
    randomness: [u8; 32],
) -> Result<()> {
    let wheel = &ctx.accounts.wheel;
    let spin = &mut ctx.accounts.spin_account;
    require!(!spin.settled, WheelError::AlreadySettled);

    // Convert randomness to selection point
    let rand_u32 = u32::from_le_bytes([
        randomness[0], randomness[1],
        randomness[2], randomness[3],
    ]);
    let point = rand_u32 % (wheel.total_weight as u32);

    // Walk segments to find winner
    let mut accumulated: u32 = 0;
    let mut winner_index: u8 = 0;
    let mut winner_multiplier: u16 = 0;

    for i in 0..wheel.segment_count as usize {
        accumulated += wheel.segment_weights[i] as u32;
        if point < accumulated {
            winner_index = i as u8;
            winner_multiplier = wheel.segment_multipliers[i];
            break;
        }
    }

    // Calculate payout: wager * multiplier / 100
    let payout = (spin.wager as u128
                  * winner_multiplier as u128 / 100) as u64;

    spin.randomness = randomness;
    spin.segment_index = winner_index;
    spin.multiplier = winner_multiplier;
    spin.payout = payout;
    spin.settled = true;

    Ok(())
}

Example 3: Prediction Market

Binary resolution via VRF Polymarket-style YES/NO markets resolved by verifiable randomness. Winners split the total pool proportionally.

Rust programs/prediction-market/src/lib.rs — Callback 
pub fn dice_callback(
    ctx: Context<MarketCallback>,
    _channel_key: Pubkey,
    randomness: [u8; 32],
) -> Result<()> {
    let market = &mut ctx.accounts.market;
    require!(!market.resolved, MarketError::MarketResolved);

    let outcome = match market.resolution_mode {
        // Binary: even byte = YES (0), odd byte = NO (1)
        0 => randomness[0] & 1,

        // Threshold: 64-bit value > midpoint = YES (0)
        1 => {
            let value = u64::from_le_bytes(
                randomness[0..8].try_into().unwrap()
            );
            let threshold = u64::MAX / 2;
            if value > threshold { 0 } else { 1 }
        }
        _ => return Err(MarketError::InvalidResolutionMode.into()),
    };

    market.outcome = outcome;
    market.resolved = true;
    market.randomness = randomness;

    Ok(())
}

Honest Assessment Transparency

No project is perfect. Here are the known limitations, trade-offs, and areas where DICE VRF is not yet production-hardened.

  • High
    Single coordinator is a centralization point. All commit/reveal transactions are submitted by one coordinator process. If it goes down, no randomness is delivered. Planned mitigation: coordinator federation with leader election, so multiple coordinators can take over.
  • High
    On-chain TX flow not fully tested end-to-end. PDA initialization and the full request → commit → reveal → finalize → callback cycle has been tested against real ESP32 hardware, but devnet PDAs are not all initialized in the current deployment state. The CPI callback path works in local validator tests.
  • Medium
    1.7-second latency. From request to callback delivery takes approximately 1.7 seconds. This is acceptable for gaming and lottery use cases, but not for latency-sensitive applications like real-time price feeds. For comparison, Switchboard price feeds update in sub-100ms — but those are data feeds, not VRF. Chainlink VRF on EVM chains takes 2-10 seconds.
  • Medium
    Minimum 4 nodes required for BFT, only 1 device tested. The protocol requires at least 4 nodes to achieve Byzantine fault tolerance (configurable up to 50). Currently, only 1 ESP32-S3 device has been tested in hardware. Multi-node coordination has been tested with simulated nodes. Real multi-device testing is pending.
  • Medium
    No TypeScript SDK yet. Integration is Rust/Anchor only. There is no @dice-vrf/sdk npm package for frontend or Node.js integration. Developers must construct transactions manually or use Anchor's generated IDL. A TypeScript SDK is planned.
  • Low
    Modular arithmetic bias in randomness reduction. Using u32 % N introduces micro-bias when N does not evenly divide 2^32. For N=6, the bias is 4 parts in 4.29 billion (negligible). For applications requiring zero bias, rejection sampling should be used — but this is not currently implemented in the example programs.
  • Info
    Channel-based (v2) is the recommended path. The v1 API (request_randomness with separate PDA per request) still works but creates more accounts and costs more rent. The v2 channel-based API (init_channel + request_randomness_v2) reuses a single persistent PDA and is what the examples target.

What Makes It Worth Using Despite These Limitations

Strengths

  • Hardware entropy — not software PRNGs
  • Commit-reveal prevents front-running
  • ECDSA signatures bind entropy to device identity
  • Multi-node combination (no single point of entropy)
  • On-chain verifiable (all data stored in PDAs)
  • Solana-native (no bridges, no wrapped tokens)
  • Open source — full audit trail

Trade-offs

  • Newer project (less battle-tested than Chainlink)
  • Smaller node network (growing)
  • No cross-chain support yet
  • Documentation still being built
  • Coordinator centralization (pre-federation)
  • Limited to VRF (no price feeds, no compute)
