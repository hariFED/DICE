Architecture Overview

DICE System Architecture

Hardware-backed Verifiable Random Function oracle on Solana. ESP32-S3 nodes generate tamper-proof entropy via a commit-reveal protocol, coordinated by a Rust server with mTLS, persisted in PostgreSQL, and settled on-chain through an Anchor smart contract.

01 / System Layers

Four-Layer Architecture

Each layer has a single responsibility. Hardware generates entropy. Firmware packages and signs it. The coordinator orchestrates timing and on-chain submission. The smart contract verifies everything and delivers randomness to dApps via CPI.

dApps
Consumer Programs — Anchor programs that call DICE via CPI. Examples: dice-roll, lucky-wheel, prediction-market, coin-toss. Receive randomness through a deliver_callback instruction or poll the DiceChannel account directly.
--- CPI (Cross-Program Invocation) ---
Smart Contract
Anchor / Solana — 21 instructions (8 v1.0 + 13 v2.0). Manages device registration, escrow, commit-reveal verification, entropy finalization, fee distribution (70/20/10), and on-chain node selection via SlotHashes sysvar.
Rust 2,961 lines programs/dice/
--- JSON-RPC (Solana RPC + WebSocket subscription) ---
Coordinator
Rust Server — Async Tokio runtime. mTLS WebSocket listener for ESP32-S3 nodes. REST API (Axum). PostgreSQL round persistence. Prometheus metrics. State machine drives each round through CollectingCommits, CollectingReveals, Finalized/Failed.
Rust 7,460 lines coordinator/
--- WSS (WebSocket over mTLS, CBOR binary frames) ---
Firmware
ESP-IDF C — Runs on bare metal. Collects entropy from hardware RNG + floating ADC pin noise. Signs with secp256k1 (mbedTLS). Manages commit-reveal ring buffer. Heartbeat loop. Captive portal for WiFi provisioning. LED status indicators.

03 / Wire Protocols

Communication Layer Detail

CB

CBOR Wire Protocol

All firmware-coordinator communication uses CBOR (Concise Binary Object Representation) over WebSocket binary frames. Messages are two-element arrays: [tag, payload]. Tags: "heartbeat", "job_assignment", "commit", "reveal", "round_result", "send_reveal".

Encoding
CBOR (RFC 8949)
Transport
WebSocket binary frames
Security
mTLS (mutual TLS 1.3)
Port
8443 (configurable)
RPC

Solana JSON-RPC

The coordinator uses JSON-RPC to interact with Solana: submitting transactions (submit_commit, submit_reveal, finalize_randomness) and watching for new requests via getProgramAccounts with memcmp filters on the RandomnessRequest discriminator and Pending status byte.

RPC URL
Configurable (devnet default)
Polling
getProgramAccounts + memcmp
Subscriptions
WebSocket accountSubscribe
Signing
Coordinator keypair (ed25519)
CPI

CPI Callbacks

Solana's Cross-Program Invocation delivers finalized randomness directly into the consumer dApp. The deliver_callback instruction is separated from finalize_v2 so randomness is safe even if the callback fails. dApps can also poll the DiceChannel account directly.

Mechanism
Anchor CPI invoke_signed
Fallback
Account polling
Retry
Separate ix, can retry safely

State Machine

Each round transitions through well-defined states with deadlines. If commits or reveals time out, the round moves to Failed. The state machine enforces that SHA-256(entropy) == commit_hash before accepting any reveal, preventing after-the-fact manipulation.

CollectingCommits --> CollectingReveals --> Finalized | Failed

Node Selection

The SelectionEngine enforces fairness and low latency:

  1. Filter to nodes with heartbeat within 45 seconds
  2. Exclude recently selected nodes (rotation fairness)
  3. Sort by latency, keep top 10 candidates
  4. Randomly shuffle and pick target count
  5. On-chain: Fisher-Yates with SlotHashes seed
06 / Firmware

ESP32-S3 Firmware Architecture

EN

entropy.c

Dual-source entropy collection. Primary: ESP32-S3 hardware RNG (thermal noise from the SAR ADC). Secondary: floating ADC pin noise (GPIO1, ADC1_CHANNEL_0) with 8 samples XOR-folded. Both sources are mixed via SHA-256 to produce 32 bytes of high-quality entropy per round.

CR

crypto.c

secp256k1 ECDSA signing via mbedTLS. Private key stored in NVS (Non-Volatile Storage) with flash encryption. Key is loaded once at boot into a singleton mbedtls_pk_context. Entropy source for the DRBG wraps esp_fill_random().

WS

websocket_client.c

Persistent WebSocket connection to coordinator over mTLS. Auto-reconnect with exponential backoff. CBOR serialization of all protocol messages. Handles inbound job_assignment and send_reveal commands.

HB

commit_reveal.c

Ring buffer of 16 pending jobs. On job assignment: generate entropy, compute SHA-256 commit hash, sign with ECDSA, send commit. On reveal command: look up stored entropy by request_id, sign, send. All operations are mutex-protected for FreeRTOS safety. 

firmware/main/
app_main.c          WiFi init, NVS, event loop, task creation
entropy.c           Hardware RNG + ADC noise -> SHA-256 -> 32-byte entropy
crypto.c            secp256k1 key management + ECDSA signing (mbedTLS)
websocket_client.c  mTLS WebSocket to coordinator, CBOR frames

07 / On-Chain State

Account Architecture (PDAs)

programs/dice/src/state/

DeviceRegistry       Seeds: ["device", device_id]
  |-- device_pubkey: [u8; 33]     (compressed secp256k1 key)
  |-- authority: Pubkey            (registrar)
  |-- registered_at: i64           (unix timestamp)

RandomnessRequest    Seeds: ["request", requester, &sequence.to_le_bytes()]
  |-- requester, sequence, status, callback_program_id
  |-- node_count, created_slot, commit_deadline_slot

CommitRecord         Seeds: ["commit", request.key(), device_id]
  |-- commit_hash: [u8; 32]        (SHA-256 of entropy)

RevealRecord         Seeds: ["reveal", request.key(), device_id]
  |-- entropy: [u8; 32], signature: [u8; 64]

RandomnessResult     Seeds: ["result", request.key()]
  |-- randomness: [u8; 32]         (SHA-256 of all entropies)

EscrowAccount        Seeds: ["escrow", requester, &sequence.to_le_bytes()]
  |-- lamports for fee distribution

DiceChannel          Seeds: ["channel", authority, &channel_index.to_le_bytes()]
  |-- status: ChannelStatus        (Idle/Pending/CommitPhase/RevealPhase/Finalized/Failed)
  |-- round_id, node_count, max_nodes (4-50)
  |-- balance: u64                 (prepaid SOL for fees)
  |-- commits[]: inline storage    (no separate PDAs in v2.0)
  |-- reveals[]: inline storage
  |-- randomness: [u8; 32]         (result stored inline)

v1.0 vs v2.0: The Channel Evolution

v1.0 — PDA per Operation
  • Separate CommitRecord + RevealRecord PDAs per node per round
  • New escrow PDA per request
  • Higher rent cost per round
  • Simple but expensive at scale
v2.0 — Channel Design
  • Single reusable DiceChannel PDA stores everything inline
  • Prepaid balance model — fund once, request many times
  • No per-round PDA creation (massive rent savings)
  • Retry-safe separate callback delivery
08 / Security

Trust Model & Security Layers

HW

Hardware Root of Trust

Private keys are generated on-device and stored in NVS with AES-XTS flash encryption. Secure Boot v2 ensures only signed firmware can run. The hardware RNG sources thermal noise from the SAR ADC — not a PRNG.

TLS

Mutual TLS (mTLS)

Private PKI with a custom Certificate Authority. Both the coordinator and each ESP32-S3 node present certificates. The coordinator rejects connections from devices not signed by the CA. WebSocket runs over TLS 1.3 on port 8443.

CR

Commit-Reveal Protocol

Two-phase protocol prevents entropy manipulation. Nodes commit SHA-256(entropy) first. Only after all commits are collected do nodes reveal raw entropy. The coordinator and smart contract both verify hash(reveal) == commit.

SIG

ECDSA Signatures

Every commit and reveal carries a secp256k1 ECDSA signature tied to the device's registered public key. The smart contract verifies signatures on-chain, ensuring no one (including the coordinator) can forge or substitute entropy values.

BFT

Multi-Node Entropy

Final randomness = SHA-256(e1 || e2 || ... || eN). Minimum 4 nodes per round. Even if N-1 nodes are compromised, a single honest node's entropy makes the final result unpredictable. The coordinator cannot bias the output.

SEL

On-Chain Node Selection

v2.0 introduces verifiable on-chain node selection using the SlotHashes sysvar. Seed = SHA-256(slot_hash || channel || round_id || block_height), used for Fisher-Yates shuffle. No one can predict or manipulate which nodes are chosen.

10 / Infrastructure

Deployment & Observability

PG

PostgreSQL

All round data is persisted: request metadata, node selections, commit hashes, reveals, final randomness, timing, and failure reasons. Required in production mode; bypassed in simulation mode.

PM

Prometheus Metrics

Six core metrics exposed on port 9090: dice_nodes_connected, dice_rounds_total, dice_rounds_failed_total, dice_round_duration_seconds, dice_solana_tx_failed_total, dice_mtls_handshake_failed_total.

API

REST API (Axum)

Endpoints: /health, /metrics, /status, /simulate. Optional API key protection via Bearer token. Rate limiting on /simulate endpoint (configurable RPS). Runs on port 8080.

DK

Docker

Docker Compose orchestrates the coordinator alongside PostgreSQL. Coordinator supports both simulation mode (no DB, no Solana RPC) and production mode (mTLS, PostgreSQL, live Solana devnet).
