Latency Report & Optimization Plan

DICE v7 · Solana devnet · 5 ESP32-S3 devices · Real-mode coordinator · Data from A2 (100 rounds) + A4 (360 successful rounds)

Why are rounds taking ~11 seconds?

Short answer: the commit-reveal protocol itself takes ~3 seconds. The other ~8 seconds are Solana devnet round-trip latency, sequential TX confirmations, and fixed polling intervals. Every one of those 8 seconds is cuttable.

The good news: phase 3 — the actual commit-reveal with 4 real ESP32-S3 devices generating entropy, signing with secp256k1, and completing the 2-round protocol — is under 3 seconds. The VRF itself is fast. Everything else is engineering choices that can be tuned down.

Why is phase 4/5/6 so slow — root cause

The F-1 fix in the stress-test session added SolanaRpc::sign_send_and_confirm, which sends a TX and then polls getSignatureStatuses every 300 ms until the TX reaches confirmed commitment. That polling loop is what's eating ~1500 ms per TX × 3 TXs = 4.5 seconds per round.

Before the F-1 fix, the coordinator used sign_and_send which returned as soon as the RPC accepted the TX. That was faster (~1 s total for all 3 TXs) but caused the race condition — TXs would land out of order. We needed a way to serialize, so we added the confirmation poll.

The fix was correct. The implementation is conservative. Three cheaper options exist.

Optimization plan — how to get to ~5 seconds per round

Target: reduce average round latency from ~11 s → ~5 s without reintroducing the F-1 race. Every optimization below is independently safe; they stack.

Optimization L1 · processed commitment wait ATTEMPTED & REVERTED

This was the obvious-looking optimization that didn't survive contact with devnet. We implemented it (sign_send_and_confirm_processed helper, both intermediate TXs switched), expected ~2 s saved per round. Failure rate jumped from 1.5 % to 5 %+ on the next run. Reverted same day.

The hypothesis: switch submit_commit_v2 and submit_reveal_v2 from confirmed (~1.5 s wait) to processed (~300-700 ms wait), keep confirmed for the final finalize+claim TX. New helper sign_send_and_confirm_processed in coordinator/src/solana_rpc.rs polls getSignatureStatuses every 120 ms and accepts any non-null entry (the entry exists at processed commitment).

Why it broke on devnet:

  • The driver and the coordinator hit different RPC nodes behind the public devnet load balancer. The driver's get_account_data at processed would observe a fresh state on its RPC instance; the coordinator's poller at confirmed would NOT yet see the same state on its instance.
  • Inside the chain commits → reveals → finalize, intermediate TXs at processed have no durability guarantee; if any one drops below the leader's bank window before the next TX is processed, the chain breaks. With 4 nodes × 3 TXs per round, the cumulative probability of one drop becomes meaningful.

What we kept: the safety win — explicit reqwest connect_timeout (8 s) and request timeout (12 s) on the coordinator's HTTP client, so a hung devnet RPC can never freeze the poller indefinitely. That bug was the secondary effect of the L1 attempt and the timeouts mitigate it permanently.

The right path to ~2 s less per round: bundle the commits + reveals instructions into a SINGLE transaction via address lookup tables (ALTs) — eliminates one full TX confirmation hop without changing commitment semantics. That's L3 below.

Optimization L2 · Shrink the DiceChannel poller interval ATTEMPTED & REVERTED

Tried 800 ms and 1.5 s, both surfaced poller-hangs under load. Combined with L1's processed-commitment changes, the tighter polling produced a tokio task that would silently freeze for minutes after a burst of "not enough active nodes" failures during node reconnection. Suspected cause: connection-pool exhaustion in reqwest when the poller and the feed crank both fire fast against the same RPC endpoint.

Reverted to the original 3 s poller interval. Required for stability on devnet's public RPC. Possibly viable on a dedicated mainnet RPC node where connection pools and request limits are higher, but not without explicit testing.

Better path: kill the poller architecture entirely and use Solana's logsSubscribe websocket subscription with a proper TLS path (the workspace's tokio-tungstenite 0.21 needs TLS feature wiring). That's event-driven instead of polled — see the dormant coordinator/src/solana_ws.rs::run_solana_ws_subscriber function which was the original design before we fell back to polling.

Optimization L3 · Bundle commits + reveals into a single TX Medium · 2 hours · saves ~1.5 s/round

Today we split because of the 1232-byte TX size cap with 4 nodes. With address lookup tables (ALTs) we can fit all 8 instructions (4× commit_v2 + 4× reveal_v2) in one TX. ALT holds the coordinator signer + channel PDA + program ID as static entries (they repeat in every instruction) and frees up ~300 bytes.

Eliminates one full TX + one confirmation round trip. Savings: ~1.5 s per round.

Optimization L4 · Remove deliver_callback for no-callback channels Easy · 20 min · saves ~1.5 s/round

Today the driver has to submit an empty deliver_callback to transition Finalized → Idle, even when the channel has callback_program_id = Pubkey::default(). That's a full TX + confirm.

Two options:

  • Option A: have the coordinator auto-call deliver_callback(empty) as part of its finalize bundle when callback_program_id == default(). Saves the driver TX entirely.
  • Option B: make finalize_v2 transition directly to Idle for no-callback channels (pair-on-chain change). Saves the entire deliver_callback instruction.

Option B is cleaner and halves the state-machine surface for streaming feeds. Savings: ~1.5 s per round for streaming / stress test / non-callback patterns.

Optimization L5 · Keep blockhash cache across TXs Easy · 1 hour · saves ~500 ms/round

Currently every call to sign_and_send does a fresh getLatestBlockhash RPC. A blockhash is valid for ~60-90 seconds. Cache for 10 s between TXs in the same round.

Savings: ~150 ms per TX × 3 TXs = ~450 ms per round.

Optimization L6 · Parallelize dispatch and state-machine pre-commit Medium · 2 hours · saves ~300 ms/round

On round dispatch, the coordinator currently writes the in-memory Round state THEN broadcasts JobAssignment. Devices can start generating entropy the moment they receive the assignment. Broadcasting first (and holding the state_machine write until the first commit arrives) shaves ~200-300 ms off the critical path.

Realistic target after the wins above: v7.1 baseline 7 791 ms → ~4 500 ms average round. All five changes together are roughly two days of coordinator + program work. The hardware-side protocol is already under 3 seconds — everything we're cutting is off-chain plumbing. Below 3 s is not possible without either reducing the node count (single-node = no commit-reveal protocol) or upgrading to faster hardware.
Hard lesson from the L1/L2 attempts: "obvious" easy optimizations on devnet RPC don't survive contact with the public load balancer. Anything below `confirmed` commitment in a multi-RPC-instance environment is a state-read race waiting to happen. ALT bundling (L3) is the safe latency win because it actually reduces the number of TXs, not the durability of each.

Why it's NOT a hardware bottleneck

  • The coordinator log field elapsed_ms measures from JobAssignment dispatch to "round finalized" (all 4 reveals collected). It averages 2900 ms across the 360 successful rounds of A4.
  • Out of that 2900 ms, the 4 devices spend ~500–800 ms each on entropy generation + SHA-256 + secp256k1 signing. WebSocket round-trip over the LAN is <50 ms per message.
  • ESP32-S3 has a dedicated hardware SHA accelerator and a hardware TRNG. Both are fast.
  • If every optimization above is applied, the protocol phase STAYS at ~3 seconds — it's the floor. That's the commit-reveal round itself, and it's what gives DICE its security.

The 11 s headline number is 75 % Solana RPC latency + coordinator-side polling, 25 % actual crypto. Flip that after the optimizations and you have a system where the crypto is the slow part — which is exactly the right shape.

How to verify

Run any stress round with timestamps enabled and grep for elapsed_ms in the coordinator log:

grep "round finalized!" /tmp/dice-coord.log | grep -oE 'elapsed_ms=[0-9]+'

You'll see values around 2800-3300. That's the real protocol time. The total round time minus that is plumbing overhead.
