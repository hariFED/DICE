1. Install

Add DICE as a dependency and enable the CPI feature.

# One dep. The `cpi` feature gives you dice::cpi::request_randomness_auto.
# `no-entrypoint` prevents entrypoint collision in your program binary.
[dependencies]
anchor-lang = "0.30"
dice = { git = "https://github.com/hariFED/DICE", features = ["cpi", "no-entrypoint"] }

2. Request randomness

Add one CPI call inside your action handler.

use anchor_lang::prelude::*;

pub fn play(ctx: Context<Play>, bet: u8, wager: u64) -> Result<()> {
    // ... your game setup: store the bet, take the wager.

    // Ask DICE for randomness. Hardware round starts instantly.
    dice::cpi::request_randomness_auto(
        CpiContext::new(
            ctx.accounts.dice_program.to_account_info(),
            dice::cpi::accounts::RequestRandomnessAuto {
                authority:      ctx.accounts.player.to_account_info(),
                channel:        ctx.accounts.dice_channel.to_account_info(),
                system_program: ctx.accounts.system_program.to_account_info(),
            },
        ),
        4, // node_count (min 4, max 50)
    )?;
    Ok(())
}

3. Handle the result

DICE calls back when the round finishes. You write one line of game logic.

// DICE's deliver_callback routes here automatically — Anchor's discriminator
// dispatch matches on the function name. Nothing else to wire.
pub fn dice_callback(
    ctx: Context<DiceCallback>,
    _channel_key: Pubkey,
    randomness: [u8; 32],
) -> Result<()> {
    let g = &mut ctx.accounts.game;

    // YOUR ONE LINE: randomness → outcome.
    g.outcome = (u32::from_le_bytes([randomness[0], randomness[1], randomness[2], randomness[3]]) % 6) as u8 + 1;

    g.settled = true;
    Ok(())
}

Channel setup · once per dApp

A channel is a long-lived PDA that binds your program as DICE's callback target. Create it once at deploy time.

// Run ONCE at deploy time. Creates a channel + pre-funds it.
await diceProgram.methods
  .initChannel(channelIndex, maxNodes, yourProgram.programId, coordinatorPubkey)
  .rpc();

// 1 SOL buys ~500 rounds at 0.002 SOL each.
await diceProgram.methods.fundChannel(1_000_000_000n).rpc();

After this, any player calling yourProgram.play() automatically triggers a DICE round. Nothing more to orchestrate client-side.

Callback payload

What DICE sends to your dice_callback handler as instruction data.

[0 .. 8]
discriminator
Anchor routes on this. SHA-256("global:dice_callback") · 8 bytes.
[8 .. 40]
channel_key
The DiceChannel PDA that produced this result · 32 bytes.
[40 .. 72]
randomness
Hardware-verified random bytes · 32 bytes · your input.

Your game account is passed as remaining_accounts[0]. Validate it in your Accounts struct as usual.

FAQ

Can I test without ESP32-S3 hardware?

Yes. tests/harness/mock_firmware_node simulates 10 devices running the real CBOR protocol and ECDSA signing. Use it for CI.

What if my callback handler panics?

Randomness is still recorded on chain (it landed in a prior TX). You can redeploy a fixed handler and replay the callback — the result isn't lost.

How do I make it provably unbiased?

Three properties already hold: any one honest device in the N-of-N set makes the output unbiasable · commits land on chain before reveals are disclosed · audit mode adds on-chain device selection. Ship with audit mode on for the strongest guarantee.

Is the randomness compatible with my EVM dApp port?

Yes. The 32-byte output matches the format Chainlink VRF and Pyth Entropy use on EVM. If you're porting a game from Ethereum, the dice_callback formula is usually a copy-paste.
