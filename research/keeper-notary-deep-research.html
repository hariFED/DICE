1.2 Clockwork SHUT DOWN

CW
Clockwork — Solana Geyser Plugin
$4M raised (Multicoin, Solana Ventures) • Died Aug 2023
DEAD

Architecture

Geyser plugin installed on validators/RPCs. Monitored "Threads" — on-chain PDAs containing trigger + instructions + SOL balance.

Thread Structure (on-chain PDA)

// Thread = automation unit
Thread {
    trigger:      Trigger,      // Account-based or Time-based
    instructions: Vec<Ix>,     // Static or dynamic via CPI
    balance:      u64,          // SOL for execution fees
    authority:    Pubkey,       // PDA from developer's program
}

Trigger Types

  • Account-based: Track byte offset in on-chain account (e.g., offset 8, size 1 for boolean)
  • Time-based: Cron expressions (*/10 * * * * * *), slot-based, epoch-based

Developer Integration

// Rust CPI from Anchor program
clockwork_sdk::cpi::thread_create(
    ctx,
    lamports_for_fees,
    thread_id,
    instructions_to_execute,
    Trigger::Account {
        address: target.key(),
        offset: 8,
        size: 1,
    },
)?;
Why it died: "Limited commercial upside." Per-crank fees (~$0.001) couldn't cover infrastructure. No token flywheel. Geyser plugin dependency made adoption hard. Key lesson: Standalone keeper product can't sustain a company. Bundling with VRF revenue is what Clockwork couldn't do.

1.3 Tuk Tuk ACTIVE

TT
Tuk Tuk — Permissionless Crank Service
By Helium team (Noah Prince) • Launched Accelerate 2025
ACTIVE

Architecture: PDAs + Bitmaps

Pure on-chain program. No Geyser plugin. Each bit in a bitmap = one task slot (1=active, 0=inactive). Crankers scan bitmaps to find executable tasks — O(N/8) bytes.

Task Queue (PDA)
  ├── capacity:      10           // max simultaneous tasks
  ├── funding:       1 SOL        // min deposit (anti-spam, refundable)
  ├── crank_reward:  5000 lamports // per execution
  ├── queue_authority: Pubkey     // who can queue tasks
  └── bitmap:        [u8; N]      // each bit = one task slot

Task Types

TypeHow It WorksUse Case
CompileV0Instructions stored on-chain ahead of timeSimple cron jobs, token transfers
RemoteV0HTTP POST to server → returns signed transactionOracle interactions, dynamic logic

Cron via Recursive Re-queuing

Execute task (Monday 10am)
  → Perform action
  → Re-queue self for next Monday 10am
  → Task stays in bitmap

Cranker: Permissionless

$ tuktuk-crank-turner \
    --solana-url <RPC> \
    --keypair-path <KEY> \
    --min-crank-fee 1000

No staking, no slashing. Just a Rust binary: scan bitmaps → find tasks → execute → get paid.

Security

  • Queue authority controls task queuing — "should not be given out blindly"
  • Remote servers must sign payloads cryptographically
  • No slashing: permissionless = best-effort, no execution guarantees

1.4 Chainlink Automation GOLD STANDARD

CL
Chainlink — checkUpkeep / performUpkeep
Ethereum • Most elegant keeper design in production
GOLD STANDARD

The Pattern

// Off-chain: runs every block, gas-free (simulated as eth_call)
function checkUpkeep(bytes checkData)
    external view returns (bool upkeepNeeded, bytes performData);

// On-chain: runs only when triggered, costs gas
function performUpkeep(bytes performData) external;
Why this is brilliant: Heavy computation happens off-chain (free) via checkUpkeep. It pre-computes results into performData. On-chain performUpkeep receives pre-computed data — minimal execution cost. This is the pattern DICE should adopt: coordinator does "check" off-chain, on-chain program does "perform".

Security (from Chainlink docs)

  • performUpkeep MUST validate all inputs — anyone can call it
  • Implement access controls restricting to Automation Registry address
  • Keep checkUpkeep deterministic and lightweight
  • Set appropriate gas limits; monitor funding balance

1.5 Gelato Network 78% MARKET SHARE

GN
Gelato — Execution Slot Model
Ethereum • GEL token for staking/governance
MARKET LEADER

Architecture: Exclusive Time Slots

Time Slot 1: Executor A has exclusive execution rights
Time Slot 2: Executor B has exclusive execution rights
  ...
If Executor A misses tasks → kicked from network

Resolver/Checker Pattern

// Off-chain: called every block
function checker() returns (bool canExec, bytes execPayload);
// On-chain: when canExec = true
function exec(bytes execPayload);

Security & Economics

FeatureDetails
StakingExecutors stake GEL to get time slots
SlashingFor censoring, front-running, or going offline
Slot exclusivityPrevents execution races; clear accountability

1.6 Solana Transaction Landing

Critical for any keeper system on Solana.

Priority Fees

Help validators prioritize during congestion. Higher fee ≠ guaranteed inclusion, but increases chances. 100% of priority fee goes to validator.

Jito Tips & Bundles

Up to 5 txs executed atomically in one slot. Min tip: 1,000 lamports. Bundles sequenced to prevent MEV. Best for time-critical executions.

swQoS (Most Effective)

Stake-weighted quality of service. Trusted connections between RPCs and validators. Materially reduces time to inclusion. Depends on RPC provider.

Best Practices

Simulate first to estimate compute units. Use Jito for MEV-sensitive ops. Standard priority for cron jobs. Reliable RPC matters more than tip size.

Part 2: Notary / Timestamping Systems

RFC 3161, OpenTimestamps, Solana Attestation Service — and what DICE can learn

2.1 RFC 3161 — Traditional Timestamping

The legal standard for digital timestamps.

1Hash Document
→
2Send Hash to TSA
→
3TSA Signs Token
→
4Return Proof
→
5Verify Later

TimeStampToken Contents

TSTInfo {
    messageImprint: hash_algo + hash_value,  // echoed from request
    genTime:        GeneralizedTime (UTC),   // claimed creation time
    accuracy:       secs + ms + µs,          // time bounds
    serialNumber:   unique integer,          // prevents substitution
    nonce:          from request,            // replay protection
    tsa:            TSA identity + cert,     // who signed
}

Legal Acceptance

eIDAS (EU), ESIGN Act (US), various national electronic signature laws. TSA certificates must contain id-kp-timeStamping as sole extended key usage.

Critical limitation: Single point of trust. If the TSA is compromised or its key is leaked, ALL timestamps become suspect. No built-in multi-authority attestation.

10,000 files timestamped with 1 Bitcoin transaction via Merkle aggregation. Trust-minimized: calendar servers can only go offline, not fake timestamps.

2.3 Solana Attestation Service (SAS)

Built by Range Security. Three-party model: Issuers (create schemas + issue), Holders (receive attestations), Verifiers (check validity). Schema-driven with revocation support.

2.4 Multi-Witness Attestation Patterns

Single Authority (RFC 3161)

Trust one TSA completely. Single point of failure. If compromised, all timestamps suspect.

Multi-Witness (DICE)

Trust threshold of witnesses. BFT: survives up to t compromised. No single point of failure.

ECDSA Aggregation Options

ApproachProsCons
Concatenated sigsSimplest. Each independently verifiable.Receipt grows with witness count
Coordinator-attestedCompact receiptReintroduces trusted party
Merkle treeRoot on-chain, proofs off-chainMore complex verification
Future: SchnorrNative multi-sig aggregationRequires firmware change
DICE already has multi-witness attestation. The VRF DiceChannel stores per-node: device_pubkeys, commit_hashes, entropies, signatures. Each ESP32 independently generates entropy, commits, signs, reveals. This IS a multi-witness scheme.

2.5 On-Chain Notarization on Solana

PDA Structure

// Attestation PDA: ["attestation", schema_id, content_hash]
pub struct Attestation {
    pub content_hash:  [u8; 32],      // SHA-256 of attested data
    pub witnesses:     Vec<[u8; 33]>, // compressed device pubkeys
    pub witness_sigs:  Vec<[u8; 64]>, // ECDSA signatures
    pub witness_count: u8,
    pub threshold:     u8,            // minimum witnesses required
    pub timestamp:     i64,           // Clock::unix_timestamp
    pub slot:          u64,           // Solana slot (ordering)
}

Cost Analysis (4 witnesses)

StrategyOn-Chain SizeRent Cost
Full attestation (all sigs on-chain)~523 bytes~0.00453 SOL (~$0.68)
Hash + metadata only (sigs off-chain)~100-150 bytes~0.002 SOL (~$0.30)
Merkle root only~80 bytes~0.0015 SOL (~$0.22)
Timestamp authority: Use both Clock::unix_timestamp (human-readable) and Clock::slot (monotonic ordering). Slot is the more reliable ordering primitive — consensus-determined and strictly monotonic.

2.6 Security Considerations

ThreatMitigation
Backdating attackBlockchain anchoring — hash in Solana slot is append-only
Compromise single witnessThreshold: min 4 witnesses (BFT: tolerates 1 compromised)
Extract hardware keySecure Boot + flash encryption + NVS encryption
Clock drift between nodesCoordinator uses Solana slots (consensus time), not node clocks
Tamper with orderingSlot-based deadlines are consensus-determined and monotonic

Hardware-Backed vs. Software-Only

PropertySoftware (server + key file)Hardware (ESP32 + NVS)
Key extractionTrivial with OS accessDifficult (flash protection)
Remote compromiseFull key via exploitCannot extract remotely
Attestation bindingAny machine with key copySpecific physical device

Part 5: Integration Architecture

How Keeper & Notary plug into the existing coordinator — zero disruption to VRF

File Structure

coordinator/src/ ├── main.rs ← spawn keeper task alongside VRF ├── keeper.rs ← NEW: trigger evaluation + execution loop ├── notary.rs ← NEW: attestation handler (~200 lines) ├── state_machine.rs ← UNTOUCHED: VRF state machine ├── protocol/messages.rs ← UNTOUCHED: CBOR wire protocol ├── queue.rs ← UNTOUCHED: VRF request queue ├── solana_watcher.rs ← UNTOUCHED: VRF account watcher ├── solana_rpc.rs ← SHARED: sign_and_send ├── solana_tx.rs ← SHARED: instruction builders ├── node_session.rs ← SHARED: node registry └── api/routes.rs ← ADD: /keeper/*, /notarize endpoints

Parallel Message Flows

VRF: Request → Select Nodes → JobAssignment → Commits → Reveals → Finalize Keeper: Timer tick → Evaluate triggers → Build tx → Submit → Log receipt Notary: POST /notarize → Select Nodes → Dispatch hash → Collect sigs → Return receipt

All three paths are completely independent. No shared state machine. The only shared resources:

  • NodeRegistry — to know which nodes are online
  • OnChainCtx — to submit Solana transactions
  • PgPool — to persist records
